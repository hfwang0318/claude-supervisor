# 带执行参考点的异步历史审查

状态：用户已批准；本仓库的 headless 提前取消接入已通过免费原生复现，最终整体验收审查待完成。禁止修改 Claude Code 宿主、冻结二进制、生成声明或全局 Router。实现与免费验证见[交付报告](../../evals/2026-10-16-historical-review.md)，未启动新付费模型测试。

本设计修订[综合审查设计](2026-10-15-complete-supervision-design.md)中“30秒共享活动预算”和“任何工作区版本前进都丢弃旧判断”的规则。其余能力目标、来源和执行安全边界继续有效。

## 用户意图与验收目标

用户提出：不要给审查模型设置超时时间；审查输出应说明结论依据的是执行到哪里的信息。主模型即使继续前进，也能根据历史意见判断是否仍需纠正。

采用以下解释：取消插件对审查模型等待施加的30秒时限，审查在主模型之外进行；正常执行前进不取消正在进行的审查，也不自动丢弃历史建议。每份输出准确说明观察截止点、实际提供的来源和未覆盖的后续执行。底层服务自身仍可能失败、断开或限制运行时间，不承诺请求一定成功或无限存活。

目标仍是研究所强调的需求—方案、方案—实现、架构、方向、探索、反例、恢复和验证判断。历史投递是这些能力的接入方式，不是以迟到建议数量替代判断质量。此前四轮没有有效判断，这个事实不变。

## 当前实现与需要改变的部分

- `Coordinator`将模型等待与取证、验证、清理一起计入每提示30秒活动预算；`ask()`把剩余额度作为`model.complete.timeoutMs`。
- `PostToolBatch`和无人模式`Stop`会等待`engineeringReview`，所以仅删掉timeout会让主模型在这些位置持续等待。
- 工具记录前进会调用`changedWorkspace`，中止当前工作；`sameBinding`要求工作区版本完全相等，因此历史建议也不能通过投递门槛。
- 已有`clock.after`、`session.append`、`prompt.submit`入口，但当前没有证据证明它们组合后可以在所有交互／headless生命周期中满足新要求。

因此本次调整同时涉及后台调度、审查参考点、有效性分类与投递，不能只改一个超时常量。

## 方案选择

| 方案 | 行为与取舍 |
| --- | --- |
| 只移除超时，继续在原hook中等待 | 修改较少，但主模型无法在等待期间前进，不满足历史审查的主要用途。 |
| 后台审查固定材料，按参考点投递 | 主模型继续执行；迟到意见保留明确历史范围，需要分开任务身份与材料版本，并验证宿主后台生命周期。采用此方案。 |
| 每次执行前进都取消并重审最新材料 | 容易持续取消、重复消耗，不符合用户保留历史判断的要求。 |

## 审查输入：由程序生成参考点

每次请求冻结一份有限、脱敏的输入。参考点由程序生成，模型不能自行选择截止位置：

- `reviewId`：本次审查的唯一标识。
- `taskRevision`及需求签名：结论属于哪一版明确需求。
- `checkpointId`、采集时间与阶段：方案、探索、实现、失败或完成。
- 最后纳入的工具调用ID、工具名称和安全相对路径（有实际记录时）；工具ID不可用时明确使用插件本地观察序号，不能伪称宿主稳定消息ID。
- 实际提供的`sourceIds`、材料签名及省略范围；有文件hash时记录原hash。截止点不表示截止前所有历史或全仓库都已审完。

当前`session.messages()`的普通消息没有稳定消息ID；`session.append`事件有宿主uuid。第一阶段优先复用已知工具ID和单会话单调递增的观察序号，不把数组下标或`record.end`冒充跨压缩的永久位置。压缩导致无法恢复旧位置时保留原参考点和“后续范围未知”，不合成事件。

提示词要求模型只依据这份材料判断，并回显`reviewId/checkpointId`。程序校验回显，且在最终反馈中附上宿主保存的参考点；不依赖模型自行描述“我已经看到了哪些后续修改”。没有显式方案时，相应一致性维度仍未审。

原始输入与诊断表示继续区分：实际请求保持必要的任务绑定；debug日志明确省略私有sessionId，不通过编码绕过宿主脱敏。缺段、其他脱敏或签名不一致仍记不可核对。

## 调度、等待与任务生命周期

1. 在原有有意义的触发点采集材料并预留调用／token额度，再交给宿主支持的后台执行入口；当前hook返回，不等待模型回复。
2. `supervise/probe/recovery`的语义审查不传插件自定的模型`timeoutMs`，也不受原30秒总活动时限取消。耗时继续记录。
3. 主模型正常生成、Read、Edit、测试，以及同一需求下的正常回合完成，只更新当前参考点，不取消在途审查。当前不可见的新材料不会悄悄追加进已发请求。
4. 每个用户提示仍最多两次模型调用、合计4000输出token；不同能力共用额度、至多一个在途工作。后续触发不为每个工具批次建立队列，只保留至多一个待考虑的最新候选，并且不保证自动发起第二次审查。
5. 不因等待时间长而自动重试、换模型、补额度或重复发送。永不返回的请求最多占用一个在途名额，可通过用户取消、关闭监督或结束会话终止。
6. 明确新用户指令／需求版本、项目身份变化、用户中断、off、主／旁路模型配置变化、插件卸载或会话结束，取消并丢弃不再属于当前任务的工作。插件自己的审查反馈不新建用户需求，也不补回预算。

这里取消的是审查模型等待时限。旁路命令、隔离复制、来源检查和清理仍有独立的有限执行预算，不能让生成命令无限运行。首个实现版本保留每提示合计30秒的工具／验证／清理活动额度，模型等待不计入；两次模型调用和输出额度不变。`existing`旧模式不在本次调整范围，历史对照解释须注明调度政策变化。

## 历史建议与当前证据分开

将原单一“完全同版本才有效”的检查拆成两种用途：

| 状态 | 判断和建议 | 新取证／执行／认证 |
| --- | --- | --- |
| 同一任务、材料版本仍匹配 | 可以投递；注明参考点 | 按原来源、快照、命令和执行预算检查。 |
| 同一任务、主模型已经前进 | 可以作为历史建议投递；当前适用性未知 | 不沿用旧绑定在当前目录自动运行旧行动，不把旧测试或事实认证为当前结果。 |
| 需求版本／会话／配置身份不符，或用户已取消／关闭 | 不投递 | 不执行，记录具体取消原因。 |

判断始终绑定最初提供的材料；不能在模型返回后读取新代码，再把新代码冒充它当时看过的证据。

历史意见附带的定位、probe或恢复行动，若已经无法通过原当前来源检查，转成明确“尚未执行、依据历史材料”的建议，交主模型决定是否重新取证。旧snapshot／source hash校验不放宽，也不自动复制或执行历史版本代码。只有独立取得匹配的当前证据，才能另外描述当前状态。

## 投递给主模型的内容

示例展示形式（示例位置和判断不代表真实结果）：

> 审查R7，依据需求第1版、执行参考点C12：最后纳入的是第12批工具结果中的`Read scheduler.ts`，只覆盖列出的来源。
>
> 你已前进到C16；C12之后的编辑和测试不在本次审查范围。当前问题是否已修复：未知。
>
> 按当时材料，方案中的独立重试与“共享刷新调度”的要求可能冲突。建议核对后续实现是否仍存在此冲突；如果已经修复或有反证，可以据此忽略或反驳本意见。

实际模板包括：审查参考点、原始引用、维度／理由／影响／建议／不确定性、未覆盖范围，以及可证实的后续执行增量摘要。不凭后续工具名称推断问题已修好，也不因代码被编辑就自动判定意见无效。

投递按`reviewId`去重：

- 主模型仍在执行：结果进入单个待投递位置，在下一个安全工具批次／模型请求边界附加；如果已无后续工具批次，使用已验证的宿主上下文追加入口。
- 主模型本回合已经回答、会话仍活跃：最多一次有明确插件来源的跟进，不冒充用户新授权，不重复唤醒。
- 用户已有新需求或会话结束：取消，不继续唤醒旧任务。
- 只记录`prepared/queued/context-returned/submitted/dropped`等实际状态；没有宿主确认，不声称主模型已经消费。

主模型处理建议时可以纠正、补证据或提出反证；记录可观察的后续动作，而非强迫执行历史建议。是否合理、是否造成回归和总开销继续作为效果指标。

## 必须先免费的宿主可行性门槛

本地类型确认`model.complete.timeoutMs`可省略，`clock.after`可调度回调；现有代码也使用这些入口。但异步模型请求是否能跨hook返回存活、如何在主模型执行中安全追加反馈，以及headless在主模型回答后是否仍保留会话，都尚未真实验证。

实现首先用同native CLI／Node／GNU loader、断网、本地固定延迟回复验证：

1. 审查等待期间主模型可以继续产生新的工具记录。
2. 原hook返回不会使后台请求被宿主自动取消；正常执行前进不终止请求。
3. 结果可在后续边界投递一次；回合结束／headless退出的实际行为得到明确回执。
4. 用户取消、off、新需求、会话结束确实取消后台工作并清理资源。

如果当前宿主不能支持其中一个生命周期，不用未等待Promise冒充可靠后台任务，也不靠无上限Stop阻塞保持会话。报告具体不支持路径并修订接入方案，再进行任何付费观察。会话已经结束后不承诺继续送达历史反馈。

## 验证与交付

- 每项状态规则先RED→GREEN；覆盖超过30秒仍可回答、主模型前进后历史投递、任务切换丢弃、取消、不重复、输入参考点伪造、材料缺失、历史probe不执行，以及总调用／token额度不被刷新。
