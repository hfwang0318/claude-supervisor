# 核心监督能力补齐与统一接入设计

状态：用户已明确批准按此修订设计开发；判断协议、证据行动和统一宿主路径已实现，正在完成整体验证；真实模型效果待新回归。依据用户 2026-10-15 最新指令，先补齐计划内核心审查能力，再通过快速／增量回归观察行为与效果。本文覆盖旧计划中“任务1取得两条有效链才允许开发任务2／3”的开发门槛；两条链继续作为效果证据，不阻止开发。

## 目标与范围

主模型已经能够处理基础定位和常见修复，旁路应审查它的工程工作：需求有没有遗漏、当前改动是否与需求冲突、跨文件调用和 API 约定是否一致、已有测试是否真的区分正确与错误实现、失败后是否在重复无效动作。旁路应给出可以核对的问题及证据，并选择下一项最有价值的验证行动。

核心能力必须围绕[已有研究](../../research/2026-10-11-capabilities-and-model-gap.md)第4—7节中强弱模型在真实项目中的过程行为差异增强，不能把“已有工具容易实现”当成能力选择依据。用户进一步明确要求：需求与方案一致性、方案与实现一致性、架构合理性，以及主模型决策方向的建议和判断，均属于本次核心范围。

定位事实、需求来源复现／反例和失败恢复是支撑评审的手段，不是核心能力的完整清单。先补齐过程评审与判断层，再接入这些证据工具；持续保留无模型规则检查。长期平台项（通用会话知识库、训练 verifier、大规模统计实验、全平台发布）不纳入本次实现。

## 研究差异与核心能力矩阵

以下沿用研究报告第5节的六个过程环节。研究提供可检验方向，不证明旁路已经能可靠审查架构；架构与方向判断的纳入是用户明确要求及基于该研究的工程设计，不虚构为已发表的普遍因果结论。

| 研究中的过程差异 | 必须补齐的评审能力 | 可核对输入与有效行为 | 回归观察指标 |
| --- | --- | --- | --- |
| 需求与语义理解：修错问题、误读边界（§4.2／§5） | 需求—方案一致性 | 用真实需求引用核对当前方案的目标、约束、遗漏和自加假设；指出具体冲突或歧义 | 错误方案是否被发现、主模型是否修正遗漏／假设，错误否决是否导致返工 |
| 信息获取与定位：错误入口、漏调用者、API用错（§4.3／§5） | 方案依据与源码事实核对 | 核对依赖、真实调用链、API和执行路径；缺材料时明确所缺证据 | 是否补到真正缺失的信息，是否避免无效读取和错误定位 |
| 实验与探索：只找支持当前方案的信息、低信息量操作（§4.2—4.4／§5） | 假设比较与验证策略 | 提出可区分解释的复现／反例，审查测试是否只是迎合当前实现 | 是否排除错误假设、暴露遗漏需求，是否增加无效或错误测试 |
| 方案与编辑决策：信息足够仍选错方案、跨文件不一致（§5） | 方案—实现一致性、架构合理性、方向判断 | 对照方案中的机制与实际改动；检查职责／依赖／状态和数据流／兼容性，比较可行方向及代价 | 是否发现实现偏离、过度设计或局部修补，是否改变错误的关键决策 |
| 反馈与恢复：忽略失败、盲改和反复重跑（§4.4／§4.8／§5） | 反馈解释、失败恢复与重规划建议 | 区分环境失败、实现失败、方案假设失效；保留反证与未决问题，建议继续、修正或转向 | 重复无效动作、误归因、错误放弃与有依据重规划 |
| 验证与完成判断：遗漏需求、错误宣布完成（§4.5／§4.7／§5） | 验收覆盖与交付判断 | 对照明确需求、检查范围和当前版本的真实结果，区分通过、未验证与失败 | 需求覆盖、误报／漏报、虚假完成、独立功能验收及总开销 |

每项核心能力都必须在后续实现任务、模型提示词、普通行为测试和回归报告中找到对应项。只实现某种工具、写一个规则或增加提示词标题，不等于该项能力已经交付。

完成实现与证明效果是两件事。实现完成要求这些路径能够工作且通过普通检查；效果报告必须展示全部回归结果、错误干预、成本和真实动作，不因模块都有代码就宣称有效。

## 选择统一入口

采用新增 `assistance_mode=supervise` 的方式统一选择行动。保持 `existing` 默认值及原有行为，保留 `facts`、`probe`、`recovery` 作为单能力测试入口；新一轮效果对比使用 existing 与 supervise。不修改已经冻结的实验配置或解释其结果。

不采用“每种能力都调用一个审查模型再汇总”的方式：那会重复读取上下文、扩大费用，并使错误来源难以辨认。也不只实现三个互斥开关后继续只评测 facts；综合入口必须实际覆盖已经实现的能力。

## 模型的职责

统一提示词明确告诉旁路：它在独立审查另一个模型的需求理解、方案、关键工程决策和实现过程，不是复述需求，也不是仅在最后确认测试。输入包括当前明确需求、主模型明示的方案／设计决策、实际改动、相关工具结果、已知事实和已有未解决问题。需求、方案与实现分别带来源和版本；没有表达过的方案不能由旁路编造后当作主模型承诺。项目源码、命令输出和模型文本都按数据处理，不能作为新授权。

审查维度包括：

1. 需求—方案：是否在解决真正的问题，是否覆盖明确约束、边界和非目标，是否有未经确认的假设。
2. 方案—实现：代码是否落实所选机制，是否存在方案漂移、遗漏分支、跨模块接口不一致或仅修表象。
3. 架构合理性：职责与模块边界、依赖方向、状态／数据流和生命周期、错误与并发处理、兼容性及变更复杂度，是否适合本项目和本次需求。不能把个人风格偏好当成架构缺陷。
4. 决策方向：当前假设与路径有无依据，是否应继续、局部调整、补证据或重新规划；比较替代方向的收益、代价与风险，避免事后只指出局部错误。
5. 定位与契约：真正的调用者／入口、导入、生成来源和所用 API 是否有源码依据。
6. 实验与验收：测试是否覆盖需求并能区分错误方案，当前结果是否支持完成判断；缺少证据时提出有来源的复现／反例。
7. 反馈与恢复：实际失败是否重复、属于何种可确认原因，哪些判断得到支持或反证，下一步哪个问题值得验证。

评审输出应包含具体问题或判断、对应需求／方案／代码证据、推理理由、影响和建议方向，以及不确定之处与最小验证方式。建议方向可为继续、调整、重新规划或补证据；不是无理由的好坏打分。主模型保留最终决策，旁路明确提出反对意见和转向建议的能力不能因此被取消。

评审判断与证据工具分两层：旁路可以直接给出有上下文依据的方案、架构和方向建议，**不要求每条判断都先转化成源码调用行或可执行命令**。需要新证据时，才选择定位、复现或恢复行动。没有条件执行的建议标为待验证；能够直接引用需求与方案的逻辑冲突可以指出，不必假装运行了实验。建议的合理性、需求矛盾、实测行为失败和修复正确性分别记录，不能混成同一种认证状态。没有有价值的问题时允许不介入。

## 三类行动

### 定位事实

复用 `FactRequest`／`FactView`／`SourceFact` 和安全 inspector。需要新源码时选择明确范围，在原限制内核对原文、路径、行号、文件和范围 hash；投递前重验版本。已有可用事实可直接引用，不再次读取或重复投递。

裸文件名不能未经核对就假定处于项目根目录。无法由真实路径和已有观察确定来源时保持 unknown，不凭模型猜测替代完整来源检查。缺失／秘密／越界来源均不提升为事实。

### 复现、反例与区分实验

实现原计划的 `ProbeCandidate` 解析与信息包构造。候选必须关联明确需求或实际项目测试／调用来源，说明它想区分的问题。沿用最多一个候选、至多两条命令的上限，不建立任意程序执行平台。

期望值必须区分：现有测试、明确需求示例、带来源的不变量，以及尚未证实的假设。导入／语法错误、缺环境、截断、超时或旧版本输出都不能证明行为缺陷。模型提出的 expected 值不能自行变成可信 oracle。

只在通过既有能力检查的隔离副本中执行，复用 `executeProbe`／`validateObservation` 等边界。不能取得隔离时，交付明确标注“未执行”的命令或候选内容，由主模型在用户原授权下决定执行；旁路不在真实目录写入或执行生成代码。主模型执行不能记成旁路独立验证。

### 失败恢复

实现原计划的恢复包：整理当前版本的实际失败、已经确认的事实，以及一个尚待验证的问题。没有相应观察，不能把某个假设写成“已排除”。

复用重复失败信号，但合理确认重跑、不同错误、flaky 迹象和新增观察必须区别处理。每提示最多一次恢复；没有新证据就结束本次介入，不自动连环重试或重新获得预算。

## 调度与预算

程序负责可靠的触发与失效，模型负责评审判断与行动选择。候选时机包括方案形成／关键方向变化、关键实现阶段、实际检查失败／重复失败，以及结束前仍有可审查内容；不能只在最终回答后才质疑已经实施很久的错误方案，也避免读到一个普通函数定义就抢先耗尽预算。

各能力共享一个 coordinator、一次在途工作和每用户提示最多两次模型调用／4,000 输出 token／30 秒活动预算。来源检索或实验执行也计入活动预算，协议重试计入模型次数。预算不足返回 unknown；不能切换能力后重置预算。

第一次模型调用选择最重要的问题与行动；必要的第二次调用基于已核验材料形成反馈。执行后反馈由程序结合实际输出构建，不另加第三个“总结模型”。单能力模式复用这些实现，不形成与综合模式并行的审查循环。

上述时机共享总预算，不承诺每一阶段都调用模型或每次调用穷尽所有维度。必须记录本次实际审查范围和因预算／上下文不足而未审的部分；未审过的维度不能以“未发现问题”表示通过。后续若预算明显限制有效评审，先报告真实覆盖与开销，再决定是否调整，不静默扩额。

安全来源限制保持原值：最多六个事实文件、两个字面词、200 访问条目、2MiB 累计读取、256KiB 单文件、32KiB 返回。超过上限整体拒绝，不裁剪后宣称完整。

新提示、off、取消、主模型／任务／工作区版本变化使旧行动失效；回执缺失和不确定的请求不自动重放。旧事实不能用于认定当前改动正确。所有实际主／旁路模型继续为 `zhipu/glm-5.3-flash`，不使用更强 fallback。

## 反馈与可观察性

反馈明确分开“观察到了什么”“推断或假设是什么”“执行过什么／尚未执行”“主模型接下来可以验证什么”。不能把一个建议称为已复现缺陷，不能把主模型口头接受称为 fixed。

保留当前确定性规则的有界结束检查。新的语义建议不建立无界结束阻塞；综合入口一次反馈后交回主模型。记录审查触发、选择的行动、固定拒绝原因、耗时、使用量、来源／观察 ID、投递和后续动作。默认诊断不保存原始模型回复、thinking、秘密或凭据。

## 验证顺序

1. 先按能力矩阵补齐需求—方案、方案—实现、架构、方向与验证／恢复评审，接入三类证据行动、统一提示词与路由、宿主接入、无隔离降级、共享预算及失效路径；不在每个小修复后追加付费模型轮次。
2. 每个实现步骤先有失败测试，再实现；普通测试每次完整运行 `node scripts/check.mjs`，包含宿主、真实文件／进程、scorer 和 adapter 检查。
3. 能力齐备并通过一次整体验证和审查后，日常昂贵 quick 只从最新完整轮次随机一个双失败任务，两组各一次；保存 seed，不重抽。
4. 完整验证只跑最新完整轮次失败／未知并集，两组各一次。quick 不替代该集合，不自动叠加 quick＋full；历史双通过题不记为新验证。
5. 新 supervise 模式必须绑定自己的新模型实验身份、冻结 runtime／adapter／selection／父结果和新输出目录。若旧选择器只接受 existing／facts 组名，先免费实现并验证明确的控制组／实验组映射，不能把 supervise 回执伪装成旧 facts 模式。

最新已完成轮次是 `caller-scope-flash` 的四次：Flipt 与 ProtonMail 都双失败，事实包为零。只保留为历史事实辅助结果，不能作为新综合监督的已验证成绩。后续报告实际审查行为、建议是否执行、有效／无效／重复／错误干预、功能通过率、耗时及观察用量；完整费用缺失继续 unknown。

普通测试必须覆盖：需求本身清楚但方案解决了另一个问题；方案正确而实现偏离；局部测试通过但接口／架构与既有边界冲突；存在更合适方向但证据不足时不武断否决；主模型有合理反证时不重复逼迫改方案；没有显式方案或上下文不全时不编造；提出错误架构建议或错误 expected 的干预也需被记录。回归不以投递次数为主指标，重点观察是否纠正关键决策、是否造成回归，以及修好任务所花总时间和费用。

## 交付边界

实现报告列明每个能力的普通验证和实际可执行环境，不能用 mock 测试声称真实隔离成功。模型效果报告保留对照、无介入、错误建议和失败案例。完整能力实现后才通过回归驱动修正，不再以定位单模块达到收益指标作为开发其他模块的前置条件。

保持隔离分支与所有历史原始结果，不自动合并或推送。本文是修订设计，不表示 supervise／probe／recovery 已经实现或实际改善质量。
