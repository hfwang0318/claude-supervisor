# 核心监督能力补齐与统一接入设计

状态：待用户审阅的修订设计；能力尚未实现。依据用户 2026-10-15 最新指令，先补齐计划内核心审查能力，再通过快速／增量回归观察行为与效果。本文覆盖旧计划中“任务1取得两条有效链才允许开发任务2／3”的开发门槛；两条链继续作为效果证据，不阻止开发。

## 目标与范围

主模型已经能够处理基础定位和常见修复，旁路应审查它的工程工作：需求有没有遗漏、当前改动是否与需求冲突、跨文件调用和 API 约定是否一致、已有测试是否真的区分正确与错误实现、失败后是否在重复无效动作。旁路应给出可以核对的问题及证据，并选择下一项最有价值的验证行动。

本次补齐原核心计划的定位事实、需求来源的复现／反例、失败恢复，连同已有需求／改动审查统一接入。持续保留无模型规则检查。长期平台项（通用会话知识库、训练 verifier、大规模统计实验、全平台发布）不纳入本次实现。

完成实现与证明效果是两件事。实现完成要求这些路径能够工作且通过普通检查；效果报告必须展示全部回归结果、错误干预、成本和真实动作，不因模块都有代码就宣称有效。

## 选择统一入口

采用新增 `assistance_mode=supervise` 的方式统一选择行动。保持 `existing` 默认值及原有行为，保留 `facts`、`probe`、`recovery` 作为单能力测试入口；新一轮效果对比使用 existing 与 supervise。不修改已经冻结的实验配置或解释其结果。

不采用“每种能力都调用一个审查模型再汇总”的方式：那会重复读取上下文、扩大费用，并使错误来源难以辨认。也不只实现三个互斥开关后继续只评测 facts；综合入口必须实际覆盖已经实现的能力。

## 模型的职责

统一提示词明确告诉旁路：它在审查另一个模型的工程改动，不是复述需求，也不是替主模型写修复。输入包括当前明确需求、实际改动、相关工具结果、已知事实和已有未解决问题。项目源码、命令输出和模型文本都按数据处理，不能作为新授权。

审查维度包括：

1. 需求覆盖与边界：明确要求是否遗漏，时间、顺序、错误处理等行为是否冲突。
2. 定位与契约：真正的调用者／入口、导入、生成来源和所用 API 是否有源码依据。
3. 实现与回归：改动是否存在可说明输入与错误结果的缺陷，是否影响已有调用或测试。
4. 测试证据：现有测试是否覆盖关键需求；缺少证据时提出有来源的复现／反例。
5. 失败恢复：实际失败是否重复，已有观察支持或排除了什么，下一步哪个问题值得验证。

输出不是笼统的“有问题／没问题”，而是 `none` 或一项带需求引用、证据引用、未验证假设与预期验证方式的行动。没有充分证据时允许不介入；模型的置信表达不替代证据。

## 三类行动

### 定位事实

复用 `FactRequest`／`FactView`／`SourceFact` 和安全 inspector。需要新源码时选择明确范围，在原限制内核对原文、路径、行号、文件和范围 hash；投递前重验版本。已有可用事实可直接引用，不再次读取或重复投递。

裸文件名不能未经核对就假定处于项目根目录。无法由真实路径和已有观察确定来源时保持 unknown，不凭模型猜测替代完整来源检查。缺失／秘密／越界来源均不提升为事实。

### 复现、反例与区分实验

实现原计划的 `ProbeCandidate` 解析与信息包构造。候选必须关联明确需求或实际项目测试／调用来源，说明它想区分的问题。沿用最多一个候选、至多两条命令的上限，不建立任意程序执行平台。

期望值必须区分：现有测试、明确需求示例、带来源的不变量，以及尚未证实的假设。导入／语法错误、缺环境、截断、超时或旧版本输出都不能证明行为缺陷。模型提出的 expected 值不能自行变成可信 oracle。

只在通过既有能力检查的隔离副本中执行，复用 `executeProbe`／`validateObservation` 等边界。不能取得隔离时，交付明确标注“未执行”的命令或候选内容，由主模型在用户原授权下决定执行；旁路不在真实目录写入或执行生成代码。主模型执行不能记成旁路独立验证。

### 失败恢复

实现原计划的恢复包：整理当前版本的实际失败、已经确认的事实，以及一个尚待验证的问题。没有相应观察，不能把某个假设写成“已排除”。

复用重复失败信号，但合理确认重跑、不同错误、flaky 迹象和新增观察必须区别处理。每提示最多一次恢复；没有新证据就结束本次介入，不自动连环重试或重新获得预算。

## 调度与预算

程序负责可靠的触发与失效，模型负责在可用行动中选择。综合入口在出现相关改动、实际检查失败／重复失败，或结束前仍有可审查改动时评估；避免读到一个普通函数定义就抢先耗尽整轮预算。

各能力共享一个 coordinator、一次在途工作和每用户提示最多两次模型调用／4,000 输出 token／30 秒活动预算。来源检索或实验执行也计入活动预算，协议重试计入模型次数。预算不足返回 unknown；不能切换能力后重置预算。

第一次模型调用选择最重要的问题与行动；必要的第二次调用基于已核验材料形成反馈。执行后反馈由程序结合实际输出构建，不另加第三个“总结模型”。单能力模式复用这些实现，不形成与综合模式并行的审查循环。

安全来源限制保持原值：最多六个事实文件、两个字面词、200 访问条目、2MiB 累计读取、256KiB 单文件、32KiB 返回。超过上限整体拒绝，不裁剪后宣称完整。

新提示、off、取消、主模型／任务／工作区版本变化使旧行动失效；回执缺失和不确定的请求不自动重放。旧事实不能用于认定当前改动正确。所有实际主／旁路模型继续为 `zhipu/glm-5.3-flash`，不使用更强 fallback。

## 反馈与可观察性

反馈明确分开“观察到了什么”“推断或假设是什么”“执行过什么／尚未执行”“主模型接下来可以验证什么”。不能把一个建议称为已复现缺陷，不能把主模型口头接受称为 fixed。

保留当前确定性规则的有界结束检查。新的语义建议不建立无界结束阻塞；综合入口一次反馈后交回主模型。记录审查触发、选择的行动、固定拒绝原因、耗时、使用量、来源／观察 ID、投递和后续动作。默认诊断不保存原始模型回复、thinking、秘密或凭据。

## 验证顺序

1. 先完成三类能力、统一提示词与路由、宿主接入、无隔离降级、共享预算及失效路径，不在每个小修复后追加付费模型轮次。
2. 每个实现步骤先有失败测试，再实现；普通测试每次完整运行 `node scripts/check.mjs`，包含宿主、真实文件／进程、scorer 和 adapter 检查。
3. 能力齐备并通过一次整体验证和审查后，日常昂贵 quick 只从最新完整轮次随机一个双失败任务，两组各一次；保存 seed，不重抽。
4. 完整验证只跑最新完整轮次失败／未知并集，两组各一次。quick 不替代该集合，不自动叠加 quick＋full；历史双通过题不记为新验证。
5. 新 supervise 模式必须绑定自己的新模型实验身份、冻结 runtime／adapter／selection／父结果和新输出目录。若旧选择器只接受 existing／facts 组名，先免费实现并验证明确的控制组／实验组映射，不能把 supervise 回执伪装成旧 facts 模式。

最新已完成轮次是 `caller-scope-flash` 的四次：Flipt 与 ProtonMail 都双失败，事实包为零。只保留为历史事实辅助结果，不能作为新综合监督的已验证成绩。后续报告实际审查行为、建议是否执行、有效／无效／重复／错误干预、功能通过率、耗时及观察用量；完整费用缺失继续 unknown。

## 交付边界

实现报告列明每个能力的普通验证和实际可执行环境，不能用 mock 测试声称真实隔离成功。模型效果报告保留对照、无介入、错误建议和失败案例。完整能力实现后才通过回归驱动修正，不再以定位单模块达到收益指标作为开发其他模块的前置条件。

保持隔离分支与所有历史原始结果，不自动合并或推送。本文是修订设计，不表示 supervise／probe／recovery 已经实现或实际改善质量。
