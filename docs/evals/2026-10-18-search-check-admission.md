# Source searches must not consume verification review opportunities

Pilot004's second semantic call occurred before its first edit. Its actual opportunity reason was `verification`, but event37 was a source search:

```sh
grep -n "invalidate\|placeholder\|loading\|isLive\|page" applications/mail/src/app/containers/mailbox/tests/Mailbox.events.test.tsx | head -40
```

Replaying that exact public tool record through production `evidenceOf` creates one successful check run. `isCheckCommand` itself returns false. The fallback for project-specific runners mistakenly treats one fragment as a runner: command splitting breaks at pipes inside the quoted grep pattern, then sees the test filename as an argument of a fictitious command. This is source inspection, not a test invocation. Incremental scheduling turns that false check into a verification milestone, which can use the otherwise reserved first-write opportunity. The second actual report contains no edit or test execution; the first-write review is subsequently skipped by the remaining budget.

The repair recognizes control operators only outside single/double quotes and outside escaped characters. It keeps the raw command slices and existing runner recognition. A real check after the search still counts. The scan does not execute commands, expand arguments, infer engineering phases or authorize a machine action. It is not a complete shell interpreter. Existing command restrictions, source/privacy gates, call/token budgets and completion reservation remain unchanged. This intentionally corrects shared deterministic check classification; it does not change legacy change formatting or global routing.

Two independent regressions reproduce the evidence error and quoted examples falsely recognized as known check commands. A host-callback regression reproduces the consequential behavior: after one ordinary review, the source search must leave the next call available for the actual first Write proposal. All three fail against the prior implementation (349passed/3failed across352host tests), and the original two failures were independently observed before the callback regression was added (349passed/2failed across351). Genuine separated check commands are positive controls.

A free original-CLI comparison runs the same synthetic stream twice, with only the command splitter changed, using frozen LinuxCLI2.1.295/Node/GNUloader, the pinned task image, network disabled and a loopback synthetic provider. At interval1 and the unchanged three-call/12000wire budget, the old product admits interval → false verification → completion. The repaired product admits interval → first-write → completion. The actual second side request includes a before-execution `proposed-change`; all three review checkpoint identities appear in later main requests (this admission gate does not archive or certify full report bodies). No candidate project commands or paid model calls run. This proves the admission mechanism, not better semantic judgment. Live operation remains interval5 unless separately changed; the synthetic interval1 is explicit test acceleration.

The strict-oracle concern was also tested independently, without changing or executing the candidate patch. Sixteen isolated examples use the task image's actual React17.0.2/Jest27.4.7. A fetch issued from an effect or microtask after the initiating callback passes the historical assertion placement after asynchronous `act`, while a direct synchronous control distinguishes them. The historical100+500+1000ms stale ladder accepts700ms and1500ms delays; the100+500+2000ms failure ladder accepts1700ms and2500ms. A second timer adding50ms also passes the broad ladder. Strict999/1000ms and1999/2000ms checks reject those mutants and accept the exact controls. These are synthetic counterexamples to the oracle's distinguishing power, not proof that a particular mutant exists in the candidate or causes its official failure. The initial diagnostic fixture produced two React callback-return warnings; brace-bodied callbacks removed them. The image's existing Browserslist age warning remains, without updating dependencies.

Current source already explicitly tells the reviewer that awaited/eventual assertions do not prove same-dispatch behavior and generous waits do not establish exact delays. Historical source availability therefore does not justify treating another stronger sentence as a validated semantic repair. The early exact-boundary advice is also not retained as a prior-review source in the completion input; whether bounded advisory continuity helps is a separate hypothesis, with potential stale-advice and material-budget tradeoffs. It is not implemented in this repair.

The next possible live question is whether preserving the first-write opportunity actually yields grounded, timely requirement/mechanism advice from the naturally available proposal rather than spending that slot on another exploration-only window. A proposal is not an executed change or an authenticated technical plan. If the natural first write contains no reviewable design decision, that dimension has no opportunity. The parser fix alone does not establish better exact-timing judgments, independent task success or cost benefit. Any paid follow-up still requires final complete engineering checks, historical replay, native/source hash binding and a fresh frozen output; no unchanged retries or full expansion.
